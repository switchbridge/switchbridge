# Инструкция для ИИ-агентов (AI Agent Guidelines)

Данный документ определяет обязательные правила и стандарты для всех ИИ-агентов, работающих с проектом **Switchbridge**.

---

## 1. Работа с ветками Git

- **Основная рабочая ветка: `ai_dev`**
  - Любые изменения, разработка нового функционала, рефакторинг и фиксы выполняются **исключительно в ветке `ai_dev`** (или фича-ветках с префиксом `ai_dev/`, например `ai_dev/feature-name`).
  - **Запрещено** коммитить напрямую в `main` или `master` без прямого и явного указания пользователя.
- **Действия перед началом любой работы:**
  1. Проверить текущую ветку:
     ```bash
     git branch --show-current
     ```
  2. Если текущая ветка не `ai_dev`:
     - Переключиться на `ai_dev`:
       ```bash
       git checkout ai_dev
       ```
     - Если ветка `ai_dev` ещё не создана локально:
       ```bash
       git checkout -b ai_dev
       ```

## 2. Фиксация изменений (Правило инкрементальных коммитов и пушей)

- **Атомарные коммиты:**
  - Не накапливайте гигантские пачки нескоммиченных файлов.
  - Фиксируйте каждый логический шаг (добавление эндпоинта, исправление бага, обновление документации) отдельным понятным коммитом по стандарту **Conventional Commits**:
    - `feat: ...` — новый функционал
    - `fix: ...` — исправление ошибки
    - `docs: ...` — обновление документации
    - `refactor: ...` — рефакторинг без изменения функционала
    - `test: ...` — тесты
    - `chore: ...` — рутинные задачи, конфиги, зависимости
- **Правило 10-го коммита (инкрементальный push):**
  - Периодически отправляйте изменения в удалённый репозиторий (`git push origin ai_dev`).
  - Не оставляйте более 5–10 локальных коммитов без отправки.
  - Обязательно выполняйте `push` по завершении каждой законченной подзадачи или логического этапа диалога.
- **Проверка перед пушем:**
  - Перед пушем убедитесь, что проект собирается и тесты проходят:
    ```bash
    npm run build
    npm test
    ```
  - Ветка `ai_dev` всегда должна оставаться в компилируемом и работоспособном состоянии.

## 3. Ведение и актуализация документации

### 3.1. Разгрузка корневого `README.md`
- Корневой `README.md` служит **витриной и точкой входа** в проект.
- В корневом `README.md` содержатся:
  - Краткое описание проекта и его назначение
  - Быстрый старт (Quickstart)
  - Общая архитектурная диаграмма
  - Ссылки на документацию отдельных подсистем
  - Дорожная карта (Roadmap) и лицензия
- **НЕ помещайте** подробные описания конкретных реализаций, подробные списки API-эндпоинтов, специфичные настройки компонентов и глубокие инструкции в корневой `README.md`.

### 3.2. Модульная документация по частям проекта
Каждая подсистема и пакет монорепозитория должны иметь собственную актуальную документацию:
- **`packages/core/README.md`** (или `docs/core.md`): ядро движка, единый формат сообщений (UnifiedMessage), маршрутизация, мостовой движок (BridgeEngine), адаптеры мессенджеров, типы контактов.
- **`packages/server/README.md`** (или `docs/server.md`): Fastify-сервер, база данных (Drizzle ORM/SQLite), схема пользователей, аутентификация (локальная + OIDC/Keycloak), WebSocket-стримы.
- **`packages/dashboard/README.md`** (или `docs/dashboard.md`): фронтенд на React/Vite, Setup Wizard, интернационализация (i18n), компоненты авторизации и мониторинга.
- **`docker/README.md`**: описание docker-compose окружения, контейнеры PostgreSQL, Redis, Keycloak, n8n и инструкции по запуску локального homelab-окружения.
- **Правило синхронизации:** При изменении логики или структуры пакета агент **обязан** обновить соответствующую документацию этого пакета.

### 3.3. Актуальность документации API
- Документация API ведётся в файле **`docs/api.md`** (или в `packages/server/README.md`).
- **Строгое правило:** При добавлении, изменении или удалении любого эндпоинта, WebSocket-события или схемы авторизации агент **обязан немедленно синхронизировать документацию API**:
  - Метод (GET, POST, PUT, DELETE, WS) и URL
  - Заголовки (Headers) и требования аутентификации (Bearer токен, сессия, Setup Mode)
  - Тело запроса (Request Body) с типами и обязательными полями
  - Формат ответа (Response Body) и коды статусов (200, 400, 401, 403, 500)
  - Пример вызова (cURL / JSON)

## 4. Чистота репозитория и безопасность

- Никогда не коммитьте:
  - Секретные ключи, токены, пароли, `.env`-файлы
  - Файлы базы данных (`.data/`, `*.db`, `*.sqlite`)
  - Директории сборки (`dist/`, `build/`) и зависимости (`node_modules/`)
- При добавлении новых утилит или библиотек фиксируйте зависимости в `package.json` соответствующего пакета.
